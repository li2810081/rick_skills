# agent_tmp.md — 在新项目里复制这套工作方式

> **怎么用**：把本文件拷到新项目根目录，改掉所有 `【填写】`。每次开新会话，在最后一节写需求。
> **人的动作只有四个**：说需求 → 确认计划 → 看效果 → 说发布。其余环节 AI 闭环完成。
> **不适用就别硬抄**：先过第 0 节的前置检查；不成立的项，本身就是你的第一条需求。

---

## 0. 前置检查（不成立就先解决它，别急着抄流程）

| 检查 | 不成立时怎么办 |
|---|---|
| 有一条命令能跑完验证（测试/自检）？ | **第一个任务是把验证变便宜**：先补最小可跑的测试或自检脚本，否则后面全靠人盯 |
| 构建产物可重复（同输入同产物）？ | 先固化构建：锁依赖、写死构建脚本、产物带版本 |
| 有"真值"可查（数据库/日志/接口/样例文件）？ | 先能只读摸到真值，否则 AI 只能猜，猜错代价高 |
| 至少有一处能跑起来（本机 / 远程机 / CI）？ | 明确在哪跑；若只能远程，把命令写进第 1 节 |
| 验收人是你？ | 若不是你，第 9 节要写清谁签字、看什么 |

## 2. 领域事实清单（最高优先级，持续更新）

> 这一节决定 AI 是「照你说的做」还是「不用猜就做对」。写完它，返工率会明显下降。

- **主数据归属**：哪些字段以本系统为准、哪些以外来系统为准；冲突时以谁为赢家
- **字段语义与单位**：每个关键字段的含义、单位、量级（例：某列数值域 0.00–0.80，实际单位是 kg 不是 g）
- **取值形态**：是布尔？是自由文本？（例：某列名义上是"是否可裁剪"，实际存的是"可裁剪 / 不可裁剪 / 有尺码线可自由裁剪"这类自由文本，按布尔处理会丢数据）
- **空值含义**：空、0、无、N/A 分别代表什么，能不能互相替代
- **业务规则**：谁能看什么、什么话不能说、哪些字段对外承诺要慎重
- **怎么查真值**：只读命令 / 接口 / 查询样例（写明"只读"）

> 维护方式：每发现一条事实就补进来；**宁可直接查真值，也不要凭名字推断**。

## 3. 三道闸门（各有变体，按项目选）

### 闸门一：测试闸
- 命令：`【填写】`
- 必须跑在隔离数据上，命令里显式指定；**禁止用默认连接**
- **把隔离做成断言**（关键）：测试引导脚本启动时校验实际连接目标，不在临时目录/测试库就直接退出。
  （某项目曾因环境变量名写错，把测试数据写进了现有库——"记得要隔离"这种提醒拦不住，只有断言拦得住）
- 全绿才算过。**失败要先判断是产品错了还是测试写得太宽**：
  - 产品行为确实变了 → 改测试，并在提交说明里写清行为变更依据
  - 只是测试选错了对象/断言过宽 → 修测试，不要改产品去迁就测试
  - **不许为了让测试变绿而直接放宽或删除断言**
- **修 bug 必须红-绿**：先提交一个能复现该 bug 的失败测试（证明缺陷真实存在），再修复让它变绿（证明修复有效、永不复发）
- 静态检查 / 迁移检查（若有）：`【填写】`

### 闸门二：冒烟闸（三选一，按项目形态）
- **A. Web UI**：起本地栈 → 用浏览器真点这几条路径：【填写 3~5 条】
- **B. exe / 桌面程序**：构建后**真实启动**一次 → 走一遍主流程 → 确认窗口、菜单、关键操作可用
- **C. API / MCP**：用真实请求打一次 → 校验返回契约（字段齐、类型对、错误码对）
- 铁律：**单元测试全绿 ≠ 可用**。历史上出过测试全过、页面点不动的事故。
- 视觉/手感/措辞这类判断**属于人**：AI 报告"我验证了什么"，人来回答"好不好看、顺不顺手"。

### 闸门三：隔离闸
- **只读可以，写入先问**：允许对生产/外部系统做只读查询取证；任何写操作前单独确认
- 生产操作前必须：**先备份**（数据 + 配置 + 当前版本标识），并写下回滚路径
- 改数据结构（类型、单位、字段含义）属于**高风险**：先说清"旧版本还能不能跑新数据"，能不给就等确认

## 4. 开发循环与停手条件

```
① 人说需求 → ② AI 只读探索 + 出计划（改哪些文件、怎么验收、有什么风险）
→ ③ 人确认计划 → ④ AI 实现（小步、可逆）→ 跑测试闸 → 自查
→ ⑤ 人看效果（本地/远程起栈，或看 AI 给出的证据）→ ⑥ 人说发布 → AI 执行第 5 节
```

**AI 每阶段都要报**：做了什么、耗时、依据（命令/文件/数据）、下一步。

**停手条件（遇到就停下来汇报，不要静默重试）**：
- 同一个问题试错 2 次仍未解决
- 需要生产写权限、需要动外部系统
- 发布过程中生产不可达 / 服务 502
- 需求边界变了，或发现计划前提不成立

**发布中服务不可达的处理协议**：
1. 先确认"是发布引起的还是本来就坏"（查上一次健康检查时间、看是否本机服务也异常）
2. 停止推进，不做任何可能扩大影响的操作（不动数据、不反复重启）
3. 用只读方式取证：容器状态、日志、端口、健康检查
4. 如实汇报：现象、时间、已排除项、需要谁介入
5. 恢复后**先复验基线**，再从断点继续

## 5. 发布仪式

**通用约定**
- 命名：版本 tag `【vX.Y.Z】`，产物 `【vX.Y.Z-短hash】`，运行时版本与之对得上
- **从 tag 干净导出构建**，避免把本地未跟踪文件、密钥、测试数据打进去
- 产物带校验和，两端比对一致再部署
- 版本号只升不改；旧版本产物与配置**保留**（回滚用）
- **回滚要演练过**：没演练过的回滚是假设。第一次发布后，找机会真回滚一次并记录步骤
- 禁止：覆盖生产配置、删除数据、跳过备份、带 `-v` 的 down

**路线 A：Docker**
1. 门禁：测试闸全绿
2. 提交本轮相关文件 → 合主干 → 打 tag → 推送
3. 干净构建镜像 → 导出产物 + 校验和
4. 备份生产：数据 dump + 配置 + 当前镜像标识（带时间戳目录）
5. 上传 → 校验和比对 → 加载镜像
6. 对齐配置中的版本号（只改版本相关行）
7. 重启 → 等健康检查通过
8. 核对数据迁移已应用
9. **刷新静态资源**（本地绑定挂载可能覆盖新资源，必须核对哈希）
10. 验收：健康检查 + 核心路径 + 关键行为抽查
11. 交付记录：版本、产物 sha、备份路径、回滚方式、未完成项

**路线 B：exe / 可执行产物**
1. 门禁：测试闸全绿
2. 提交 → 合主干 → 打 tag（版本号同时写进程序元信息/关于页）
3. 干净构建 exe → 产物 + 校验和（确认无调试残留、无内置测试数据/密钥）
4. 备份：现有可执行文件 + 配置 + 数据（若程序带本地数据）
5. 分发/替换：保留旧文件并改名留档（如 `app-vX.Y.Z.exe` 与 `app-prev.exe`）
6. **真实启动冒烟**：双击/命令行启动一次，走一遍主流程，确认无报错弹窗
7. 验收：核心功能 + 版本号显示正确
8. 交付记录：版本、产物 sha、旧版留档路径、回滚方式

## 6. 多机器与状态交接

- **能接手的都落仓库**：进展、踩坑、发布记录都写进仓库文件，别只留在某台机器或工具记忆里
- 约定文件（可自定名）：
  - `docs/TRAPS.md` 踩坑库（第 7 节）
  - `docs/RELEASE.md` 发布与回滚步骤（第 5 节的填好版）
  - 需要在会话间续接时，写一份简短 `PROGRESS.md`：当前状态、下一步、未决问题、怎么验证
- **每台机器的环境怪癖单独标注**（例："A 机器：python 必须加 `-S`"），换机器先看这栏
- 密钥与访问权限：仓库里只写"存在哪、怎么用"，**不写值**

---

## 7. 踩坑库（仓库为源，工具记忆互备）

- **源在仓库**：`docs/TRAPS.md`，一条一节，写清「现象 → 根因 → 怎么做 → 为什么」
- **同时写进工具记忆**（若工具支持持久记忆）：两处互为备份，换机器/换工具都不丢
- 该记：环境怪癖、部署陷阱、命令的正确写法、业务规则、外部系统契约、用户偏好与纠正
- 不该记：代码结构本身（代码里有）、一次性的临时信息
- 示例：
  - 「某机器 python 启动崩溃 → 某 `.pth` 文件按 GBK 解码失败 → 命令加 `-S`」
  - 「容器重建后页面仍用旧 JS → 本地目录挂载覆盖了镜像内静态资源 → 重建后必须重新收集静态并核对哈希」
  - 「健康检查返回 400 其实是正常的 → 生产要求带 Host 头 → 用域名头再测」

## 8. 给 AI 的硬边界与报告要求

- 提交只含本轮相关文件；本地数据、缓存、临时产物**不要提交**
- 未提交的改动先问归属，**不擅自提交、不擅自丢弃**
- **不擅自合并主干、打 tag、部署**——只有人明确说"发布"才执行第 5 节
- 不擅自改生产配置、不擅自改权限；需要时说明理由 + 回滚方式，等人确认
- 报告如实：失败就说失败并贴证据；跳过哪一步要写出来；**不许把"接口报错"说成"已通过"**
- 每个关键节点报「做了什么 / 耗时 / 依据 / 下一步」；试错 2 次即停
- 涉及数据、权限、外部系统的操作，先给「影响 + 回滚」再动手

## 9. 发布前验收清单（逐条打勾，缺项=未完成）

- [ ] 全量验证在隔离环境通过（记录结果与耗时）
- [ ] 静态/迁移/安全检查通过
- [ ] 冒烟闸按项目形态走过一遍（浏览器 / exe 启动 / 真实请求）
- [ ] `git status` 核对：本轮只动了预期文件
- [ ] 产物从 tag 干净构建，不含密钥或本地数据
- [ ] 生产已备份（数据 + 配置 + 旧版本标识），路径已记录
- [ ] 部署后健康检查正常、日志无异常
- [ ] 关键行为在生产抽查过（只读方式）
- [ ] **人确认过效果**（AI 不能自认验收通过）
- [ ] 回滚方式和材料写在交付报告里（已演练过更佳）
- [ ] 未完成/存疑项明确列出，不含糊
