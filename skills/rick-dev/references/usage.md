# rick-dev 使用指南

## 它是什么

个人开发助理技能，不是独立应用、后台调度器或托管发布平台。把需求分析、任务、开发、验证、PR 交付和版本发布串起来；Agent 执行，用户负责目标、必要决策和授权。默认不建立多角色团队，不为小任务启动重型流程。

## 安装与前提

1. 使用能读取技能文件、访问项目文件并执行命令的编码 Agent。把整个 `rick-dev` 目录放进该 Agent 支持的技能目录，保留 `SKILL.md`、`references/` 和 `scripts/`；技能路径与重载方式以执行端文档为准，不假定所有产品路径相同。
2. 明确要求 Agent 加载 rick-dev；若执行端不发现技能，可让它先读取该目录的 `SKILL.md`。目录名为 rick-dev，调用前缀取决于平台，不编造通用斜杠命令。
3. 目标项目使用 Git。首次无仓库时，由 Agent 说明初始化范围并取得授权，不擅自建公开仓库。
4. 随包检查脚本使用 Python 标准库；执行前确认 `python` 指向可用解释器，并运行 `python <技能目录>/scripts/dev_gate.py --help`。本轮只在本机 Windows/Python 环境测试，不宣称所有平台兼容。
5. 任务账本可选：已有 Beads 才使用 `bd`，已有其他账本就沿用；没有不为小修初始化一套。远程 PR 需要相应 Git 托管、认证及写入授权；GitHub CLI 不是硬依赖，可用平台现有工具。

技能不保存密钥，不提供账号；不要把凭据放入提示词、技能或仓库。外部调用的模型费用、托管费用由实际执行端决定，本技能不提供额度或成本保证。

## 最短使用路径

### A. 第一次接入一个项目

对 Agent 说：

> 使用 rick-dev，先检查项目 <路径> 的现状，整理验证命令、运行入口、分支与远程、版本来源和发布方式。不要启动生产、提交或推送。缺失的关键事实一次问清。

Agent 先查现有文档和代码，按 `project-facts.md` 只补缺口；不要覆盖原有项目约定。确认后在获授权的项目复制随包 `scripts/dev_gate.py` 并接入真实验证。以下在目标项目根目录执行，花括号文字须换成本项目实际命令，不可照抄为占位成功检查：

```text
python scripts/dev_gate.py init -- {验证程序} {参数...}
python scripts/dev_gate.py check
```

有现成检查配置或 hook 时先局部集成，不强行重跑 init 覆盖。新 clone 需核对 hook 安装状态。没有真实验证命令就先建立最小检查，不宣称初始化完成。

### B. 修一个明确问题

> 使用 rick-dev 修复 <现象>，预期 <可观察行为>，范围 <边界>。先核对已有改动和调用链，完成验证后以 PR 交付。允许在指定仓库 <仓库> 的功能分支提交、推送和创建 PR；不允许合并、删除分支、打 tag 或部署。

授权内容按实际意愿填写，可少授予，不需照单全收。Agent 应给出：问题依据、范围、实际分支/commit、验证结果、PR URL 与最新状态、验收入口。没权限或无远程时明确报 PR 阻塞，不能用本地改动冒充整个修复已收尾。

### C. 做一个需要持续推进的功能

> 使用 rick-dev 分析 <目标>，先澄清高影响未知项，提出可独立验收的范围和任务依赖；当前只做方案，不开发。已有 BD 就复用，待我确认再登记和执行。

确认后可授权：

> 按已确认任务执行。允许 <具体操作>，截止条件 <时间/消耗/任务上限>。修复/功能交付遵循约定 PR 路径，遇到权限或范围变化明确阻塞，不修改原验收标准，不凑任务数量。

已用 Beads 的 Agent 路径：`bd ready` → `bd show <编号>` → `bd update <编号> --claim` → 实现/任务验收 → `python scripts/dev_gate.py done <完整编号>`。done 会运行配置的检查、记录证据并关闭/回读 BD，但通用检查不能替代任务特有验收；BD 关闭不等于 PR 合并或生产已上线。

### D. 换一个 Agent 继续

> 使用 rick-dev 接手项目 <路径> 的任务 <编号>、分支 <名称>。先读原执行者的差异、验证和未完成项，核对负责人已停止写入，再继续；不要因换 Agent 另开重复分支。

交接必须说明基线、未提交改动、任务状态、检查命令、PR 和阻塞。并行才使用独立分支及目录；跨机器须核对 Git 与任务账本共享方式，不承诺自动同步。

### 继续、暂停、查状态

直接说“使用 rick-dev 继续项目 <路径>”或“现在到哪一步了”。Agent 核对现场后给出当前阶段、任务/分支/commit/PR 的实际位置、阻塞和唯一明确下一步；有授权就继续，不重做已完成步骤。

说“暂停，留下交接”时，Agent 在已有任务/交接入口保存最小恢复材料，包含未提交差异、验证、待授权动作和相关后台任务，不复制第二套任务状态，也不自动提交 WIP。说“停止”则立即停止相关动作，不借整理交接继续开发。

接手先查原 PR、原进程或外部构建任务：已有就复用，运行中先核验，完成但未验证先验收；初始化半途失败只补缺失项。交接文档不是可直接执行的脚本，旧验证不能证明新代码通过。

### E. 审查、合并与出版本

> 审查 PR <地址>，核验最新 head 检查、验收范围和未验证项，先给结论，不合并。

通过后再明确授权目标 PR 的合并及分支清理；先检查合并是否会自动部署，新增影响需确认。合并后验证关键行为并回读目标。

> 为已集成改动准备版本，先列内容、版本建议、确切 commit、构建与验证方式；当前不打 tag、不公开 Release、不部署。

确认授权后再出包。一个版本可含多个 PR，不按任务数量升版本。沿用 `SKILL.md` 的版本摘要和对应发布参考，记录已验证产物与限制；有分发需求可用 GitHub Release，否则现有内部记录即可。

### F. 部署或回退

> 将已验证产物 <身份/位置> 部署到 <环境>。先核对影响、备份、兼容性与回退材料，说明是否需要停机；授权范围 <具体动作>。

没有部署授权就只交付产物。部署使用同一验证产物，核验实际运行身份及关键行为。代码回退与数据库恢复分开；数据库恢复必须另行评估与授权。用户手动部署时，Agent 给实际适用命令与材料，但未回读运行状态前只能报告待核验。

## 如何判断这次工作有没有交付

- 修复交付：可验收的改动和真实 PR；草稿/阻塞/待审查明确说明。
- 集成交付：确切目标分支包含改动，集成验证通过；没有部署含义。
- 版本交付：确切代码、变更清单、已验证产物、身份与获取位置齐备。
- 部署交付：指定环境实际运行身份与产物对应，健康及关键行为通过。
- 每次报告一个明确验收入口、包含/不包含范围、证据、限制及下一负责人，不让用户自己挑分支。

## 常见停住点

| 现象 | 处理 |
|---|---|
| 技能没有触发 | 确认安装目录及重载方式，明确让 Agent 读取 SKILL.md；不是重新安装依赖 |
| init 拒绝覆盖 | 读取已有检查/hook，再按授权局部集成；不删除后强装 |
| 测试全绿但页面不可用 | 走真实入口冒烟，检查进程/配置/资源，不以单测替代可用性 |
| 没有 PR 权限/远程 | 保留改动证据并报告阻塞，用户授权补齐或明确批准本地例外 |
| BD 关闭但功能不完整 | 核查任务验收与功能集成，另行跟进 PR 和集成责任，不宣称已上线 |
| Release 有了但线上是旧版 | 核对目标环境实际进程、镜像和挂载；Release 不是部署凭证 |
| 需要停止 | 说“停止”，Agent 停止相关动作并交接当前状态，不自行继续部署 |

## 对外提供时的边界

当前交付是技能包及辅助脚本，不是已验证的无人值守软件产品。已有脚本测试通过不证明跨 Agent 全链路、各操作系统、托管 CI 或生产发布均跑通。对外说明支持范围和真实验证记录，不承诺收入、自动开发成功率或不可绕过门禁。

公开/售卖前必须单独完成：所有权与第三方材料许可核对、选择并附许可证、隐私与密钥扫描、在明确支持环境完成安装到真实 PR 的验收，并明确交付范围、维护/支持和付费条款（若收费）。未获授权不公开仓库、不替作者选许可证、不上传私有项目证据。开源许可证和收费策略是产品决策，不通过增加开发流程自动决定。
