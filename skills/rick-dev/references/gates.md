# 三道闸门（细节与写法）

## 闸门一：测试闸

**要求**
- 一条命令跑完整验证；命令里**显式指定**隔离数据位置，不依赖默认连接
- 全绿才算过
- **修 bug 必须红-绿**：先提交一个能复现该 bug 的失败测试（证明缺陷真实存在），再修复让它变绿（证明修复有效、永不复发）。这是 TDD 中对本类项目回报最确定的一条
- 失败先判断性质：
  - 产品行为确实变了 → 改测试，并在提交说明里写清行为变更依据
  - 测试选错了对象 / 断言过宽 → 修测试（**不要改产品去迁就测试**）
  - 不许为过测试而放宽或删除断言

**把隔离做成断言（关键）**

"记得要隔离"这种提醒拦不住事故。某项目曾因环境变量名写错（用了 `DJANGO_DB_NAME`，
实际只认 `DJANGO_SQLITE_PATH`），基准脚本把测试数据写进了现有库。正确做法是**跑测试前断言连接目标**：

```python
# Django 例子：放在测试引导处
import os, tempfile
from pathlib import Path
path = os.environ.get("DJANGO_SQLITE_PATH", "")
if not path or Path(path).parent != Path(tempfile.gettempdir()):
    raise SystemExit(f"拒绝运行：测试库必须在临时目录，当前={path!r}")
print(f"[test] 使用隔离库: {path}")
```

```bash
# 通用例子：任何技术栈都能用
case "${APP_TEST_DB:-}" in
  /tmp/*|"$TMPDIR"/*) echo "[test] 隔离库: $APP_TEST_DB" ;;
  *) echo "拒绝运行：请把 APP_TEST_DB 指向临时目录" >&2; exit 1 ;;
esac
```

**判断"是产品错了还是测试写宽了"**
- 断言的是**业务规则**（权限、金额、状态机）→ 大概率产品错了
- 断言的是**实现细节或取样对象**（比如"取第一个属性"结果取到了新属性）→ 大概率测试写得太宽
- 拿不准时：先复现用户能看到的那个现象，用事实判断

## 闸门二：冒烟闸（按形态选）

**A. Web UI**：起本地栈 → 浏览器真点 3~5 条核心路径 → 记录每条的结果
**B. exe / 桌面程序**：构建后**真实启动**一次 → 走主流程 → 确认窗口/菜单/关键操作可用、无报错弹窗、关于页版本号正确
**C. API / MCP**：用真实请求打一次 → 校验返回契约（字段齐、类型对、错误码对、鉴权对）

**铁律**：单元测试全绿 ≠ 可用。历史上出过"测试全过、页面点不动"的事故。

**分工**：视觉、手感、措辞属于**人**。AI 报告「我验证了什么」（DOM 结构、接口返回、数量、状态），
人回答「好不好看、顺不顺手」。**AI 不能自认验收通过。**

**注意**：截图/自动化接口本身可能失败，此时要明确说"视觉验收未完成"，
不能用 DOM 检查冒充视觉通过。

## 闸门三：隔离闸

- **只读可以，写入先问**：允许对生产/外部系统做只读查询取证；任何写操作前单独确认
- 生产操作前必须**先备份**：数据 + 配置 + 当前版本标识，落到带时间戳的目录并记录路径
- **改数据结构属高风险**（字段类型、单位、含义）：先说清"旧版本还能不能跑新数据"，能不给就等确认
- 外部系统回写（若项目有）：白名单控制、只写人工改过的值（防回环）、失败不阻断本地但必须留日志
- 数据源优先级写死在项目事实里：**谁是主，冲突时以谁为准**
