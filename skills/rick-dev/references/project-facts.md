# 新项目接入：前置检查 + 访谈清单 + 骨架文件

## 一、前置检查（不成立就先解决它，别急着抄流程）

| 检查 | 不成立时怎么办 |
|---|---|
| 有一条命令能跑完验证？ | **第一个任务是把验证变便宜**：先补最小可跑的自检/测试 |
| 构建产物可重复（同输入同产物）？ | 先固化构建：锁依赖、写死构建脚本、产物带版本 |
| 有"真值"可查（数据库/日志/接口/样例文件）？ | 先能只读摸到真值，否则只能猜，猜错代价高 |
| 至少一处能跑起来（本机 / 远程 / CI）？ | 明确在哪跑，把命令写进 AGENTS.md |
| 验收人是发起人本人？ | 若不是，在验收清单里写清谁签字、看什么 |

## 二、访谈清单（一次问清，别边做边问）

按顺序问，答案直接写进 `AGENTS.md`：

1. 项目做什么、给谁用？技术栈？
2. 仓库/主干分支/功能分支命名？能否直接提交主干？
3. 在哪台机器上怎么起？（命令 + 访问方式；若多台机器，逐台记怪癖）
4. 测试怎么跑？（命令、隔离方式、预期结果）
5. **部署形态**：Docker 还是 exe？产物放哪、谁执行发布？
6. 生产在哪（主机/目录/域名/分发路径）、怎么判断它健康？
7. 配置与密钥有哪些、存在哪（**只写位置，不写值**）？
8. 哪些东西绝对不能碰（生产库、生产配置、用户数据…）？
9. **领域事实**：哪些数据以本系统为准、哪些以外来系统为准？关键字段的单位与取值形态？空值代表什么？
10. 有没有外部系统交互（只读？可写？写权限有没有）？

## 三、要生成的仓库文件

### 1) `AGENTS.md`（项目事实，越短越好）
```markdown
# <项目名> · 开发约定

## 命令
- 起本地：`<命令>`  → 访问 `<地址>`
- 跑验证：`<命令>`（隔离方式：`<环境变量/临时目录>`，预期：<结果>）
- 检查：`<命令>`

## 部署
- 形态：Docker | exe
- 目标：<主机/目录/分发路径>
- 步骤与回滚：见 `docs/RELEASE.md`

## 绝对禁止
- <生产库写操作 / 覆盖生产配置 / 提交本地数据文件 …>

## 机器备注
- <机器A>：<环境怪癖>
- <机器B>：<环境怪癖>
```

### 2) `docs/TRAPS.md`（踩坑库，仓库为源）
```markdown
# 踩坑库

## <一句话现象>
- 根因：
- 怎么做：
- 为什么：
- 机器/环境：（若只在某台机器出现）
```
同时把**通用性强的条目**写进工具记忆（跨项目复用），两处互为备份。

### 3) `docs/RELEASE.md`（发布与回滚，含真实命令）
按 `release-docker.md` 或 `release-exe.md` 的骨架填成本项目的命令；
每次发布后补一行记录：版本、产物 sha、备份路径、结果、异常。

### 4) `PROGRESS.md`（需要跨会话续接时才建）
```markdown
# 进度
- 当前状态：
- 下一步：
- 未决问题：
- 怎么验证：
```
用完即删或归档，不要长期堆积。

## 四、接入后的第一次闭环

建议第一次就做一件**小而完整**的事（改个文案、调个显示），把「需求→计划→实现→验证→确认→发布」
走通一遍。流程跑通比一次改很多东西有价值。
