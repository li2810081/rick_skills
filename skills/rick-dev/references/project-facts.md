# 新项目接入：前置检查 + 访谈清单 + 骨架文件

## 一、前置检查（不成立就先解决它，别急着抄流程）

| 检查 | 不成立时怎么办 |
|---|---|
| 有一条命令能跑完验证？ | **第一个任务是把验证变便宜**：先补最小可跑的自检/测试 |
| 构建产物可重复（同输入同产物）？ | 先固化构建：锁依赖、写死构建脚本、产物带版本 |
| 有"真值"可查（数据库/日志/接口/样例文件）？ | 先能只读摸到真值，否则只能猜，猜错代价高 |
| 至少一处能跑起来（本机 / 远程 / CI）？ | 明确在哪跑，把命令写进 AGENTS.md |
| 验收人是发起人本人？ | 若不是，在验收清单里写清谁签字、看什么 |

## 二、项目事实清单（先查仓库和环境，只问影响当前任务的缺失项）

已有事实直接复用，不要求用户重复回答；缺失且影响当前决策时集中询问，答案写进 `AGENTS.md`：

1. 项目做什么、给谁用？技术栈？
2. 仓库/主干分支/功能分支命名？能否直接提交主干？
3. 在哪台机器上怎么起？（命令 + 访问方式；若多台机器，逐台记怪癖）
4. 测试怎么跑？（命令、隔离方式、预期结果）
5. **部署形态**：Docker / exe / 定时任务 / 脚本 / Web / API / MCP / 其他？产物放哪、谁执行发布？
6. 生产在哪（主机/目录/域名/分发路径）、怎么判断它健康？
7. 配置与密钥有哪些、存在哪（**只写位置，不写值**）？
8. 哪些东西绝对不能碰（生产库、生产配置、用户数据…）？
9. **领域事实**：哪些数据以本系统为准、哪些以外来系统为准？关键字段的单位与取值形态？空值代表什么？
10. 有没有外部系统交互（只读？可写？写权限有没有）？

## 三、要生成的仓库文件

### 1) `AGENTS.md`（项目事实，越短越好）
```markdown
# <项目名> · 开发约定

## 命令
- 起本地：`<命令>`  → 访问 `<地址>`
- 跑验证：`<命令>`（隔离方式：`<环境变量/临时目录>`，预期：<结果>）
- 检查：`<命令>`

## 部署
- 形态：Docker | exe | 定时任务 | 脚本 | Web | API/MCP | 其他
- 目标：<主机/目录/分发路径>
- 步骤与回滚：见 `docs/RELEASE.md`

## 绝对禁止
- <生产库写操作 / 覆盖生产配置 / 提交本地数据文件 …>

## 机器备注
- <机器A>：<环境怪癖>
- <机器B>：<环境怪癖>
```

### 2) `docs/TRAPS.md`（踩坑库，仓库为源）
```markdown
# 踩坑库

## <一句话现象>
- 根因：
- 怎么做：
- 为什么：
- 机器/环境：（若只在某台机器出现）
```
同时把**通用性强的条目**写进工具记忆（跨项目复用），两处互为备份。

### 3) `docs/RELEASE.md`（发布与回滚，含真实命令）
按实际形态选 `release-docker.md`、`release-exe.md` 或 `release-other.md`，填成本项目的命令、回滚触发条件、兼容性及授权范围；
沿用主文件版本摘要：出版本时追加 tag/commit/集成基线、相对上一版本的变更及关联 PR/BD、不包含项、产物位置/身份、验证和限制；部署后追加环境/时间、旧版本/备份、实际运行身份核验、结果及回退。出版本与部署分开授权和报告，不另建一份任务完成账本。首次接入核对版本唯一来源、PR/CI 入口、必需检查及绕过权限、自动构建/发布/部署触发条件；只核查记录，不因此自动修改仓库规则或启用自动部署。

### 4) `PROGRESS.md`（需要跨会话续接时才建）
```markdown
# 进度
- 当前状态：
- 下一步：
- 未决问题：
- 怎么验证：
```
用完即删或归档，不要长期堆积。

## 四、初始化可执行检查（新项目/首次接入必做）

1. 先检查项目已有验证入口、Git `core.hooksPath`、pre-commit 和 CI。能复用就复用，不叠加第二套。验证须确认数据及外部副作用隔离；脚本本身不替应用验证隔离。
2. 从本技能 `scripts/dev_gate.py` 复制到目标仓库 `scripts/dev_gate.py`。确定项目真实验证命令后运行：`python scripts/dev_gate.py init -- <可执行文件> <参数...>`。它创建 `scripts/dev-check.json` 和实际 hooks 目录中的 pre-commit；已有配置/hook 时拒绝覆盖，由 Agent 局部集成。命令使用参数数组；需要 shell 时明确指定本机实际 shell。不自动初始化 BD、不提交、不推送。
3. 运行 `python scripts/dev_gate.py check`；真实验证失败会非零退出，且不允许验证过程修改源码/暂存区。项目产物目录应按实际情况忽略。确认 Python 可用；已有测试框架不另建一套。
4. 任务的验收检查应纳入项目检查入口，或先独立执行并记录。完成任务使用 `python scripts/dev_gate.py done <完整BD编号>`：重跑项目检查，保存时间、命令、输出、HEAD 和工作区指纹，再执行关闭并回读状态。通用检查通过不自动证明任务特有验收满足。证据在 Git 本地元数据里，可能含隐私，不自动上传；跨机器交接须审查后另保存必要证据。
5. 在隔离测试仓库确认失败检查能阻断提交/关闭，成功检查可以继续。把初始化、验证、BD 完成命令及绕过限制写进项目 `AGENTS.md`。新 clone 的 Git hook 不会随仓库自动启用，须再次检查/初始化；已有 dev-check.json 时手工复用配置并安装 hook，不能覆盖原 hook。
6. 涉及 GitHub PR 的项目，按授权配置已有 CI 和必需检查，绑定确切 commit。本地 hook 可被 `--no-verify` 跳过，BD 包装也可被直接 `bd close` 绕过；不是权限安全边界。
7. 发布时才按实际形态生成项目发布脚本，复用既有发布入口；使用真实构建、校验和及回退步骤，不复制通用占位脚本。开发验证绑定 commit，不要求先打 tag；正式发布遵循项目版本策略与授权。

## 五、接入后的第一次闭环

第一次选择一件小而完整的真实改动，跑「需求→任务→分支实现→验证→按授权 PR/审查→合并复验」；修复须遵守主文件强制 PR 及阻塞规则。确有版本交付需求时继续出包/记录，确有部署需求和授权时再部署核验，不为演示流程操作生产。每阶段分别报告证据；未跑的后续阶段标待验证，不把文档齐备称为全链路已跑通。
