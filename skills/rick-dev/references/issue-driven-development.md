# Issue 驱动开发与规格工具接入

用于需求登记、自动拆解、持续开发、测试与发布的流水线设计。本文是复用与验收约定，不是已部署或已通过长时间运行测试的证明。

## 1. 先盘点，再选工具

1. 读项目 `AGENTS.md`、`docs/TRAPS.md`、`docs/RELEASE.md`，记录本项目验证命令、数据隔离方式及发布边界。
2. 先查项目实际任务系统和执行端：已有 BD 就读取任务与依赖，不为调研引入 Kanban。仅在项目已采用或明确拟接入 Hermes Kanban 时，加载 `hermes-kanban-ops` 并按当前工具文档只读检查；以下命令只适用于该分支，使用前核对本机 CLI 帮助：
   ```bash
   hermes kanban boards show
   hermes kanban --board <board> list --json
   hermes profile list
   hermes -p <worker> skills list
   ```
3. 区分三种证据：框架文档说明支持、当前配置允许、真实任务已经跑通。不要互相替代；旧卡片的角色名也不能证明当前有同名 profile。
4. 列出登记、拆解、依赖、执行、审查、CI、发布、通知各环节已有实现和缺口。已有调度器就沿用；只有具体缺口才引入新工具。
5. 方案讨论期间不创建执行卡、不安装工具、不修改 Worker。先确认方案及副作用范围，再接入隔离试点。

## 2. 分工与状态归属

推荐起步是主脑调度、开发、验收三种职责；复用已有 Worker，不按前端、后端、架构、PM、QA、发布各建一个 Bot。普通子代理用于短任务，持久 Worker 承担跨会话开发。执行端可以是 Hermes，也可以调用用户选定的其他 coding agent；工具选择不改变测试和发布门槛。

| 对象 | 负责的事实 | 不负责的事实 |
| --- | --- | --- |
| Issue / 需求卡 | 需求入口、问题描述、讨论、外部引用 | 仅凭关闭状态证明产品已可用 |
| 批准的 spec / plan | 需求范围、用户场景、技术决策、验收目标 | 根据开发失败自行降低要求 |
| tasks 文档 | 稳定任务编号、依赖、需求引用、计划改动 | 与看板各维护一套独立完成状态 |
| 项目选定的 BD / Kanban | 任务、依赖、阻塞、验收状态与交接；实际调度能力取决于执行端 | 仅凭状态或 Worker 声明替代验证，也不默认自动启动执行者 |
| 测试 / 冒烟 / CI 记录 | 对应代码版本的实际行为证据 | 自动授予合并或生产发布权限 |

维护需求→任务→验证证据的映射；同步重复事件时按项目和稳定任务标识去重。任务文档中的勾选若保留，应是已验收状态的派生视图，不成为第二个调度器。不要同时手工维护 Issue、Task Master、tasks 文档和 Kanban 四套任务状态。

角色与目录隔离不等于操作系统安全隔离；按 `hermes-bot-profile-setup` 核验工具面、凭证及执行环境。验收者以独立上下文和实际证据检查，不以换了模型或人设作为独立性证明。

## 3. 按需调用 Spec Kit

小修复不强制走完整规格流程。大功能、跨模块或持续多阶段交付，按以下顺序使用上游能力；命令拼写以所选版本和 Agent 的实际集成为准。

| 步骤 | 可复用能力 | 交付与边界 |
| --- | --- | --- |
| 明确目标 | `speckit-specify` | 按优先级描述可独立验收的用户场景、功能要求、成功条件、假设和范围 |
| 澄清缺口 | `speckit-clarify` | 只询问会改变实现或验收且无法从现有证据查到的问题；把答案写回规格，不为凑提问数反复追问 |
| 技术设计 | `speckit-plan` | 记录真实栈、接口契约、约束和改动位置，先引用既有项目事实 |
| 生成任务 | `speckit-tasks` | 稳定编号、需求/用户场景引用、依赖、具体文件；并行标记须经实际调用链与文件冲突检查 |
| 开发前检查 | `speckit-analyze` | 检查规格、方案、任务的矛盾、覆盖缺口和无需求依据的任务；输出分析，不静默改需求 |
| 实现后补漏 | `speckit-converge` | 对照原意检查 missing / partial / contradicts / unrequested；上游采用追加任务而非重写旧任务的约定 |

将补漏 findings 交主脑登记为可追踪的返工卡；验收者不通过修改产品代码或原规格来批准自己的结果。需求范围确需改变时，走明确的需求变更，而不是伪装成补漏。

### 接入检查

1. 先读所选版本的 README、模板、集成源码和 customization 文档，记录采用版本；不能沿用旧博客的命令、版本或能力判断。
2. 优先使用上游现有 Hermes / ZCode 等适配；安装路径、加载方式和权限行为仍需核对当前版本，不因文档列了 Agent 名就宣布可用。官方集成已核对的行为：Hermes 适配把技能装到 `~/.hermes/skills/speckit-*`，调用必须用连字符名（`/speckit-specify` 有效，`/speckit.specify` 点号形式不被识别），且安装后须重启 Hermes 才刷新技能发现——"装完命令不出现"先查这两点再排查别的；ZCode / Codex 适配装到项目 `.zcode/skills/` / `.agents/skills/`，前缀是 `$speckit-<command>`。
3. 将适配器实际写入目录与目标 profile 的技能发现路径逐项对照；查清安装、升级和卸载是否影响全局或其他项目的技能，再授权执行。不要假定主 profile 能加载就代表 Worker 能加载。本机实测多个技能根并存且均为活根（`~/.hermes/skills/`、`%LOCALAPPDATA%/hermes/skills/`、`~/.agents/skills/`，各有技能从对应根正常加载），Hermes 适配默认落点 `~/.hermes/skills/` 可用；换机或升级后用 ls 各根 + 对照样例技能是否加载复核。
4. 区分 CLI 初始化与 Agent 技能执行。CLI 用于建立项目结构和集成文件；不要编造一个“生成任务 API”或把 Agent 内的技能命令当普通终端命令。
5. 让项目宪法明确引用/映射现有 `AGENTS.md` 和 rick-dev 规则，避免两份互相矛盾的约束。差异优先使用上游 preset 或项目级 override；接外部系统才考虑 extension，不为一次接入造完整 SDK。
6. 显式覆盖上游 tasks 模板中测试可选的默认行为：非平凡逻辑至少一个可运行检查，按 L1/L2 风险补充验证；不得为通过测试降低断言。
7. 复用项目已选 BD 或 Kanban 为任务状态依据，执行端沿用既有约定；不为 Spec Kit 再启第二套调度。Spec Kit 的分析和收敛是 Agent 工作流程，不是机器级权限或完成闸门。

## 4. 最小试点与验收

授权后在隔离测试仓库先走一个完整用户场景，再扩成长任务。验证：

- 目标 Worker 真能加载指定技能，生成的规格/方案/任务无未替换占位符。
- 核心需求有任务和验证证据，任务依赖符合真实执行顺序。
- 同一需求重复登记不重复派工；审查失败不会标 done，重试有上限。
- 中断后能读回有效进度、产物和失败记录，再决定恢复，不宣称原进程仍在连续运行。
- 规格补漏没有偷偷改需求；机器验证与真实主流程均有结果。
- 验收通过只到本轮声明的阶段；合并、推送、发布、生产重启仍按 rick-dev 和当前授权执行。

试点没有真实运行证据时，只能报告“方案已整理”或“待验证”，不能写“闭环已跑通”。
