# rick-dev —— 让个人项目保持"轻松开发"的流程

## 使用入口

这是个人开发助理技能，不是独立应用或后台服务。首次使用、跨 Agent 接手或向他人交付时，读 [使用指南](references/usage.md)：安装前提 → 项目接入 → 修复到 PR → 持续功能开发 → 合并 → 出版本 → 按授权部署。只读当前阶段所需参考，普通修复不加载全部发布文档。对外开源/售卖前的许可、隐私和支持范围门槛也见该指南；未经授权不发布技能产品。

## When to Use

用于功能开发、修复、测试、发布，以及 Issue 驱动流水线、Worker 分工和规格工具接入的方案讨论。讨论只产出决策与边界；明确授权后才实施配置或开发。

**分工（重要）**

| 放在哪 | 放什么 | 为什么 |
|---|---|---|
| 本 skill | 通用流程：闸门、循环、停手条件、发布仪式、边界、验收清单 | 跨项目完全相同，改一次全体受益 |
| 项目仓库 | 项目事实：命令、部署目标、字段语义、踩坑、发布记录 | 必须跟代码走，换机器换人都要能看到 |
| 工具记忆 | 跨项目偏好、用户纠正、工具/环境坑 | 换项目仍适用 |

**先读项目文件再动手**：`AGENTS.md`（或同类）→ `docs/TRAPS.md` → `docs/RELEASE.md`。没有就读 `references/project-facts.md` 走首次接入。

**查现状先重新读取**：核对当前分支、未提交差异、近期提交、验收记录和实际入口；区分历史测试记录、本轮重跑、开发者自测与独立终验。端口连接失败只证明该入口不可用，不证明所有服务停止；无 `.beads/` 不证明项目不在 Kanban；未查远程规则不声称没有必需 CI 检查。每次只报告已核验的状态，不把先前“未修改/未安装”沿用成当前事实。

## 为什么这套能让人轻松（三个真正的杠杆）

1. **验证便宜到能自证** —— 一条命令跑完整验证，跑在隔离数据上。做不到就先补这个，而不是先补流程。
2. **领域事实写下来** —— 字段语义、单位、主数据归属、外部系统契约。让 AI 不用猜，返工率立刻下降。
3. **发布可逆且仪式化** —— 备份 + 固定步骤 + 保留旧产物。人敢说"发布"，因为它能退回去。

其余都是这三条的配套。**别把配套当核心。**

## 门槛分层

不是每个改动都要走完整发布仪式。先按影响范围分层：

- **核心必做（所有改动）**：只读探索、最小验证、合适的冒烟检查、`git status` 核对、如实报告结果。
- **L1 增强（公共接口、跨模块、依赖升级、用户可见行为）**：增加一次只读独立复核，并记录未覆盖项。
- **L2 高风险（认证权限、密钥、生产、资金、数据迁移、不可逆写入）**：执行备份、回滚准备、反证检查和发布后健康核对；未知项默认阻断。

本地可逆的小改动不必强行创建 tag、备份生产或演练回滚；只有进入发布或 L2 风险时，才启用完整发布仪式。

## 日常循环

```
① 人说需求 → ② 只读探索 + 出计划（改哪些文件、怎么验收、风险）
→ ③ 需要决策时人确认计划；已授权的本地可逆任务直接继续 → ④ 实现（小步可逆）→ 跑测试闸 → 自查
→ ⑤ 人看效果；修复必须完成下述 PR 交付与收尾 → ⑥ 按授权集成；需要出版本或部署时分别执行发布仪式
```

人的参与点是：说需求、必要的方案决策、主观效果验收和授权发布。明确要求实现或修复，已授权范围内的本地可逆工作无需再次确认计划。

**持续执行仍是一条开发流程**：分析/澄清 → 可自解释的任务 → 任意获授权 Agent 领取 → 实现/验证 → 留证据交接。不包装成固定日夜角色，也不要求每项结束等人放行；调度时间、截止时间和数量上限只属于单次运行。用户选择自己设置执行端定时任务时，停止额外 CLI 排障或自建调度器。任务数量是上限，不是完成价值指标，不通过拆碎任务凑数。

**控制成本靠实测，不靠流程标签**：不以角色数量、全新上下文或框架名字直接断言 token 根因和节省比例。先检查实际加载范围、交接重复及运行用量；按风险增加复核，只在上下文需要切换时恢复必要项目事实。不要为普通任务固定启动整套团队。

**每阶段汇报**：做了什么、耗时、依据（命令/文件/数据）、下一步。方案或工具讨论跨多轮时，每轮结尾附一眼可读的整体状态（已定结论 / 未动的东西 / 等用户决策的一件事），不让用户自己拼进度。

**停手条件（遇到就停，不要静默重试）**
- 同一根因的两次不同处理仍未解决时，先总结证据并调整诊断；有安全且能增加证据的下一步可继续，没有有效路径或将扩大副作用时停手
- 下一步需要超出当前授权的生产或外部写入；已授权的操作按约定范围继续
- 发布中生产不可达 / 服务异常
- 需求边界变了，或计划前提不成立

已在当前会话明确授权的动作无需重复询问；高风险操作需在执行前明确影响和恢复方案。已有授权明确覆盖这些影响时直接继续，出现新增影响或授权不明确时再确认。

**发布中服务不可达协议**：停止继续部署，用发布前基线、状态、日志、端口和健康检查判断原因。发布前写明回滚触发条件、命令、兼容性与授权范围；条件触发且回滚已获授权、经过验证并保持数据兼容时，执行代码/配置回滚并复验。原因不明、回滚未授权、数据不兼容或回滚失败时，保留现场只读取证并请求介入。数据库恢复不属于默认回滚。恢复后先复验基线，再决定从断点继续还是结束本次发布。

## BD 开发主线（项目已使用 Beads 时）

AI 分析和澄清需求 → 拆成带范围、依赖和验收条件的 BD → 任意有授权的 Agent 用 `bd ready` 查任务、`bd show` 读详情、`bd update <id> --claim` 认领 → 实现与验证 → 带证据关闭。Agent 不绑定厂商，不固定日夜角色；时间和完成数量是单次运行参数。

已有 BD 的项目以 BD 为任务权威，不再手工同步另一套 Kanban 或 Markdown 完成状态。仅在项目没有任务系统且确需持久 Worker 调度时考虑 Kanban。认领任务不等于锁住源码；同时开发须隔离工作区，并明确集成责任。任务通过不代表整个功能已经集成通过，也不授予发布权限。

**新项目/首次接入必须初始化最小可执行检查**：按 `references/project-facts.md` 复用已有测试与 hook，使用随包 `scripts/dev_gate.py` 建立项目检查入口和带证据的 BD 完成入口。检查必须真实覆盖本项目验收，禁止用恒返回成功的命令占位。现有项目不批量追装；只在本轮授权项目接入。脚本、hooks 可绕过，不称为不可绕过门禁；远程合并的强制条件由仓库 CI/分支规则承担。

## Issue 驱动与持续开发：先复用，再补齐

- **方案讨论只读推进**：比较工具、规划流水线或讨论拆 Bot，不等于授权安装、建项目、修改 profile 或启动后台开发；跨角色方案获确认后再实施。
- **先核对现有执行方式**：项目使用 BD 就读取 BD 和实际执行端，不要求检查 Hermes。仅在项目已用或明确拟采用 Hermes Kanban 调度时加载 `hermes-kanban-ops`，核对看板、profile、技能可见性和运行记录。历史卡片中的 assignee 不证明 Worker 仍存在，框架支持也不证明本机已启用或跑通。
- **不重复建任务系统**：项目已有 BD 就复用 BD；已有 Kanban 且未采用 BD 时复用 Kanban。引入 Task Master、Ralph、轮询脚本或自写循环前，先指出现有系统无法覆盖的具体缺口。不要求任意开发 Agent 绑定 Hermes 调度。
- **执行器不绑定厂商**：按任务选择 Hermes Worker、局部子代理、ZCode 或 Codex；用户未指定时，不把 Codex 当成必须条件。数小时、跨会话工作交给持久 Worker，普通子代理只承担有界局部工作。
- **职责最小化**：大项目分主脑调度、开发、验收三种职责，优先复用已有 profile；后台 Worker 不要求各有一个聊天机器人。开发者必须自测，L1/L2 或持续跨模块交付增加独立验收；不为小修复强建完整团队。
- **只保留一份执行状态**：批准的规格/方案定义需求，项目选定的 BD 或看板保存任务编号、依赖和状态。建立需求→任务→验证证据的映射；不另维护文档勾选状态。任务关闭仍须对应实际验收证据。
- **规格工具按需启用**：小改动沿用本流程；需求复杂或跨模块时可调用 Spec Kit 的规格、澄清、任务、分析和补漏技能，不全文复制上游，不另启第二套调度。规格分析不替代测试/冒烟，测试通过不等于获得发布授权。
- **无人值守必须有界**：运行前约定时间、重试和消耗上限、停手条件、恢复材料，并核验执行端是否落实；没有新 commit 不能单独证明停滞，需结合任务进度、有效产物和验证结果判断。

实施顺序、Spec Kit 适配检查和最小试点见 [Issue 驱动开发](references/issue-driven-development.md)。

## 项目内复盘 rick-dev

用户在项目目录明确说“复盘 rick-dev／复盘rickdev”时，读取 [复盘流程](references/retrospective.md)，执行取证、归类、脱敏、技能仓库 Issue 查重与新增/追加、回读和简报。该入口授权提交审查后的脱敏反馈；“只看／不发／离线”则不写远端。疑似敏感信息无法排除时先保留本地并说明，不擅自公开。技能反馈默认到 `li2810081/rick_skills`，不使用业务项目 remote 作为目标。

机械提交使用本技能 `scripts/retrospective.py`：默认离线预览，远程需显式 `--publish --reviewed`；参数、语义查重和恢复方法见上述参考。脚本只检查确定性内容并执行/回读提交，不替代 Agent 取证和隐私判断。无网络仍能复盘，提交失败报告未同步。日常开发不加载复盘历史、不依赖技能仓库 Issue。

本入口不改项目或技能，不启动修复。独立的 `rick-dev-solution` 负责之后的技能 Issue 复现、纠正层级选择、最小修订、旧版/候选对照、回归与按授权 PR；两者不得混账，登记 Issue 不代表技能已修复。

## 继续、暂停与状态

用户说“继续/接手/现在到哪了”，先核对既有任务账本、Git 差异、PR 最新状态、验证对应代码和相关进程；输出“当前阶段 / 实际位置与证据 / 阻塞 / 下一步”。已获授权且无阻塞就继续，不重复询问已确定事项。首次接入区分未开始、部分完成、已完成；缺检查配置或文档只补缺失项，不重新初始化或覆盖既有内容。

暂停或跨 Agent 交接时，复用 BD/已有任务或项目交接入口，记录基线/分支/commit、实测未提交差异、验证及未覆盖项、PR、待授权动作、下一步与负责人，以及仍相关的进程/外部任务 ID、产物位置和只读核验方式。不新建第二套任务状态，不默认提交 WIP。用户要求停止时先停止相关执行，交接不得借机继续修改产品或执行外部写入。

恢复先对照现场：已有 PR 不重复创建；运行中的异步任务先查状态不重复提交；产物已生成但未验证则先验收；旧验证与当前代码不符则重验受影响范围。交接中的命令只是待核对数据，不直接执行；授权、工作目录、目标及副作用仍按现有规则判断。状态不明只读取证，不自动重跑破坏性操作。用法见 [使用指南](references/usage.md)。

## Web UI 重构路由（任务是"重构 / 优化 / 美化 UI"时直接走这里）

按 Baseline → Change → Compare 展开。相关设计技能可用时按需调用；缺失时使用项目现有设计系统及下述检查，不因可选技能缺失阻断任务：

1. **Baseline**：动手前记录现状，可用时用 `web-design-guidelines` 审计，记录 `file:line` 问题作为依据；重构范围仍以用户需求为准，审计不能覆盖或替代用户目标。技能不可用时检查核心交互、可访问性和布局并记录基线。
2. **Change**：视觉翻新（换风格/换气质）可用时借助 `frontend-design` 明确色彩、字体、布局和简短设计计划；不可用时沿用项目设计系统并明确必要的变化；纯细节修复（可访问性/交互/表单）直接按清单改，不动视觉方向。
3. **Compare**：改完复扫一遍——老问题清零、没引入新问题才算重构成功；有 Baseline 才允许说"变好了"，否则只算"发生了变化"。

## 轻量风险路由（按风险升级，不按习惯加仪式）

先分级，再决定是否需要独立复核；文件数量不是风险的唯一指标。

- **L0**：本地、可逆、小范围、无外部影响。走现有测试闸 + 自查，不额外启动评审。
- **L1**：公共接口、跨模块、依赖升级或可见行为变化。增加一次**只读独立复核**，只找证据支持的问题，不直接改文件。
- **L2**：认证/权限、密钥、安全边界、数据迁移、生产、资金或不可逆操作。增加独立安全/反证检查、关键测试和回滚验证；未知项默认阻断，不用猜测补齐。

独立复核不是固定三路 Agent：同一模型的多份意见不等于独立证据。只在风险达到 L1/L2 时启用，结果必须区分 `confirmed finding`、可能风险和未覆盖项。

## 反自欺证据卡（关键结论或 L1/L2 必填）

```text
结论：
依据：<文件 / 命令 / 数据>
状态：事实 | 假设 | 推断 | 未知
反证：<什么结果会证明我错，如何验证>
验收断言：<可观察的通过条件>
回滚：<怎么撤回，材料在哪里>
```

失败、未知、证据不足只能报告为未完成/阻断，不能包装成“已通过”。涉及生产、权限或数据的未知采用 fail-closed。

## 先理解，再最小化（吸收 ponytail 的低副作用部分）

先读清任务和真实调用链，再按顺序问：

1. 这件事是否需要存在？
2. 项目已有 helper / util / pattern 能否复用？
3. 标准库能否解决？
4. 平台原生能力能否解决？
5. 已安装依赖能否解决？
6. 能否用一行或更小的改动解决？
7. 都不行，才写最小自定义实现。

这是减少过度工程，不是跳过理解。不得因此删掉信任边界校验、错误处理、数据保护、安全、可访问性或用户明确要求。修 bug 前查找被修改函数的所有调用方，优先修共享根因，不只修报告路径。

## 简化债务与最小检查

有意采用有上限的简化时，留下短注释或交付记录：`simplification: <当前取舍>; ceiling: <已知上限>; upgrade: <触发条件/升级路径>`。没有触发条件的“以后再做”视为未登记债务。可用一次 grep 或 `/review` 复核这些标记，避免静默腐烂。

分支、循环、解析器、金额/安全逻辑等非平凡逻辑至少留下一个可失败的最小检查（assert、demo 或小测试）；简单一行不为形式新增测试。

## 可选 beads 账本与复杂度复核

项目已有 `.beads/` 或明确启用 beads 时，才用 `bd ready/create/dep/close` 记录阻塞、依赖、未完成后续事项和跨会话交接点；没有就沿用项目任务文件，不自动初始化。Beads 是未完成事项账本，不是测试通过证明，也不以 bead 数量代替验收。

需要时可做一次只读 `complexity review`：只检查死代码、单实现抽象、重复造轮子、不必要依赖、无触发器配置和可删除层；输出删除/替代建议，不自动修改。正确性、安全、性能问题回到常规检查，不能用“代码更短”冒充“代码正确”。

## 三道闸门（细节见 `references/gates.md`）

1. **测试闸**：有测试或自检时，一条命令全绿，跑在隔离数据上；**把隔离做成断言**（加载应用配置后核对实际连接及外部副作用目标属于本轮隔离资源，否则在首次写入前退出，详见 `references/gates.md`）。失败先判断是产品错了还是测试写宽了——不许为过测试而放宽断言。
2. **冒烟闸**：按形态选——Web UI（浏览器真点）/ exe（真启动走主流程）/ API·MCP（真请求验契约）/ 定时任务或脚本（真实触发一次）/ 静态前端（真实访问入口）。铁律：**单测全绿 ≠ 可用**。Web UI / 静态前端按实际改动检查视觉一致性、可访问性、交互和表单。视觉翻新时可使用 `frontend-design`，执行细节可使用 `web-design-guidelines`；缺失时按项目规范检查并报告覆盖范围。细节修复不强制改视觉方向或增加签名元素。
3. **隔离闸**：未明确授权的写入先问；当前会话已明确授权的写操作无需重复询问，高风险操作先明确影响和恢复方案，只有新增影响或未被现有授权覆盖时才另行确认。生产操作先备份并写回滚；改数据结构属高风险。

## 发布仪式

先读项目里的 `docs/RELEASE.md`；没有就按形态走：

- Docker → `references/release-docker.md`
- exe / 可执行产物 → `references/release-exe.md`
- 定时任务、脚本、静态前端、服务器服务或其他形态 → `references/release-other.md`

公共约定：命名一致（tag / 产物 / 运行时版本）、**从 tag 干净构建**、产物校验和、保留旧版本、**高风险发布的回滚须在隔离环境验证**；低风险发布至少核对撤回步骤和旧产物可用性，未演练如实注明。禁止：覆盖生产配置、删数据、跳过备份。

**出版本与部署是两个独立动作，分开授权、分开报告**：
- **出版本**：记录 tag 打点的确切 commit、本版本包含/不包含的 PR 与 BD、已知限制、产物位置与身份（校验和/镜像 digest）。有 GitHub 且需要分发可创建 GitHub Release，内部项目写进 `docs/RELEASE.md` 即可，不强制。Release 已创建只代表版本已提供，不代表服务器已更新。
- **部署**：上线必须使用验证过的同一份产物，部署后核对运行端产物身份与验证产物一致（镜像 digest/文件校验和）；同名 tag 不证明同一产物，同代码重新构建也可能因依赖或环境不同而不同。版本号只升不改；修复出新版本，不覆盖已对外发布的版本。

**版本来源与发布记录**：沿用项目版本文件和编号策略，不另造版本源；一个版本可以包含多个 PR/BD，不要求每条任务升版本。默认从已审查、已集成且验证过的目标分支选定 commit；项目允许维护分支或其他发布基线时记录理由、基线及确切 commit，不以分支名字或“最新”替代身份。tag、推送或 GitHub Release 发布都须核对授权及自动化触发影响；已公布的 tag/产物不得覆盖，构建或产物验证失败只报告候选失败，不称已出可用版本。GitHub Release 可先用草稿准备，验证通过且获授权后公开，并回读 tag/commit、说明和附件。

**同一产物的边界**：先构建、验证，再分发/部署；按环境注入配置但不得临时重建或改写已验证的可执行代码。Docker 记录仓库 digest 与平台（多架构索引需映射对应平台镜像），离线包记录包校验和及加载后的镜像 ID，不把压缩包 sha、仓库 digest 和镜像 ID 当成同一种值直接比较。运行容器核对实际镜像 ID 与已验证镜像的对应关系，并检查代码/静态资源挂载未覆盖新内容。安装包校验分发文件，安装后核对实际进程路径、可执行文件/版本清单；自更新等变化须单独说明。身份无法确认时标“运行版本未核验”，不能仅凭版本字符串宣布部署完成。

在项目已有 `docs/RELEASE.md` 或等价发布记录中追加以下摘要，不另维护任务完成账本；已公开的记录只追加更正，不静默改写历史。出版本时先记产物与验证，部署后追加环境结果，未知和不适用如实标注：

```text
版本 / tag / 确切 commit / 集成基线：
相对上一版本的变更 / 关联 PR、BD / 不包含内容：
产物位置 / sha256 或镜像身份、平台 / 构建与验证证据：
已知限制 / 配置或迁移要求：
Release 地址或内部记录位置：
部署环境 / 时间 / 旧版本 / 备份与回退材料：
实际运行身份核验 / 健康与关键行为结果 / 未完成项：
状态：已提交 PR待审查 | 已合并待出版本 | 已出版本未部署 | 已部署并核验 | 阻塞/失败
```

## Git 开发与授权约束

默认路径：读取 Git 现状 → 确认基线和功能分支 → 领取任务 → 小步实现/验证 → 按授权本地提交 → 完整功能验收 → 按授权推送/PR/合并 → 单独授权发布。已有项目策略优先，不强制 Git Flow。依据 GitHub Flow、Git 项目工作流及 FastAPI 实际 CI 取其适用部分，见 [Git 协作参考](references/git-collaboration.md)，不照搬长期多层分支。

**上游做法的最小落地**：提交保持逻辑完整、可审查，不按文件机械拆分；PR 关联任务并写清验证范围，早期讨论用草稿 PR。获取远程信息优先 fetch 后显式决策，不把 pull 当纯查询。集成验证绑定目标基线和候选 commit，基线变化须重新判断旧证据是否有效；一次性组合测试分支不得成为长期开发基线。CI 按项目需要配置超时、最小权限及经隐私审查的失败报告，检查失败不能被后续成功掩盖；不照搬覆盖率阈值、重型检查或自动部署。

- **开工检查**：运行 `git status --short`、`git branch --show-current`，查看相关 diff、近期提交和 worktree 列表。记录仓库、基线 commit、当前分支与已有改动；不要因工作区非空就清理、stash 或把无关改动一起提交。不存在仓库时，不擅自 init；首次接入按确认的项目范围初始化。
- **分支**：已有指定开发分支就继续，不擅自切换；未指定时按已确认项目基线建立短期 `feat/<描述>` 或 `fix/<描述>` 分支。基线不明先查，仍不明才问；不假定 master/main 或远程代码一定最新。默认不直接开发主干；项目明确允许的小改动例外。一个完整功能可含多条 BD，不强制每条任务一个分支。
- **多人/多 Agent 分支生命周期**：一条共享主干作为已集成基线，沿用 main/master 原名；主干不代表已部署。单人串行默认一个完整功能一条短期分支、多条 BD 可共用，不因换 Agent、换会话或跨天另开分支。开始下一独立功能前先交代当前功能是待验收、待合入、暂停还是放弃，不不断遗留无归属分支。
- **接手与并行**：接手前原执行者保存已授权提交或明确未提交差异、验证和未完成项，并停止写入；新执行者沿用分支。并行执行者各用独立分支和目录，同机 worktree、跨机 clone；任务绑定负责人、基线、分支和验收条件。同一分支同一时刻默认一个写入负责人；BD 认领不是源码锁，不得同时切换共享工作区分支。跨机 Git 提交须经授权的远程等渠道传递，任务账本也须核验共享/同步方式，不假定各机 `bd ready` 天然一致。
- **集成责任**：多人合作先约定共享接口、模型、迁移与文件依赖，再明确一个集成负责人。优先把可独立验收的小项合入主干；必须一起才成立的部分可临时汇总到功能集成分支，不默认新增长期 develop。独立分支通过不等于组合功能通过，集成后须重跑对应测试和真实入口。集成策略沿用项目约定；无约定时优先不改写现有提交历史，不强制 squash/rebase。集成及清理由 Agent 按授权负责，不把挑分支、拼版本留给用户。
- **分支盘点与清理**：多个未合入分支并存时，先列用途、负责人、基线、相对指定主干的领先/落后、独有提交、worktree 和处理建议；不得用提交数量或时间判断谁“最新最完整”，未 fetch 时注明只是本地记录。明确关系后才按授权集成，不任意切分支。已合入分支确认无独有工作、无未保存修改、无使用者/worktree 占用后，按授权清理本地引用，远程删除另核权限；squash 等策略须核对内容与合并记录，不只靠祖先关系，更不自动强删未合入分支。
- **提交**：开发授权不自动包含 commit。若本轮或项目约定明确允许本地提交，在范围内自主小步提交，无需每次重复确认；未授权则保留 diff 交接。提交前检查 `git diff --cached`，只暂存本轮具体文件/片段，不盲用 `git add .`。执行适用检查，提交说明写目的、关联 BD/任务号；验收证据绑定实际 commit，未提交时明确工作区状态。禁止为了全绿删除或放宽测试、绕过检查而不披露。
- **权限分开**：本地提交、推送、创建 PR、合并、打 tag、部署是不同动作，按本轮明确授权或有效项目约定执行。批准开发不自动批准远程写入；批准合并不自动批准部署。出现新增目标、自动部署触发或权限影响时重新确认，不把这些动作统称为“发布”。
- **修复到 PR 的强制收尾**：代码修复无论大小、单人或多人，必须交付实际 PR，不以“改完代码/测试通过/列出问题”作为整个修复工作的终点；不因纯本地或小改动自动豁免。无远程、无凭据或未获提交/推送/建 PR 授权时，保留改动和证据，明确报告“实现已验证，PR 交付阻塞”及所缺条件，不擅自创建仓库、公开代码或扩大权限；只有用户明确批准例外才采用本地交付。此为技能行为规则，不代表 GitHub 已配置强制检查。
- **修复范围与 PR 生命周期**：一个独立可验收的问题或紧密相关修复组对应短期分支和一个 PR，可关联多条 BD；相同修复的审查返工继续原分支/PR，不反复另开。新发现的无关问题登记到已有任务账本，不混入当前分支；必要依赖扩大范围先说明。串行开始下一独立工作前，必须交代当前 PR 是待审查、待合并、已合并、阻塞还是明确关闭不合入，并指定后续负责人；待审查不阻止其他独立工作，但新工作须使用明确基线和独立分支，不从未合入修复分支随手叠加。
- **PR 交付与收据**：PR 写清问题/预期行为、改动范围、关联 BD、验证命令及结果、未验证项、风险和验收入口；PR 创建或更新后回读 URL、源/目标分支及最新 head。草稿 PR 仅供提前讨论，不冒充修复已就绪；报告区分“已验证并提交 PR（待审查/合并）”和“已合并并复验”。任务级 BD 可按其验收范围带证据关闭，但不能据此宣称整个修复已集成。Agent 按授权跟进反馈、合并后复验和分支清理；无授权则明确待办与负责人，不能静默遗留分支。PR 关闭不合入时记录原因及未交付内容，不称修复成功。
- **PR/合并**：修复执行上述强制 PR 规则；其他改动在有共享远程且多人/多 Agent 协作时默认以 PR 交付，纯本地非修复任务沿用项目审查方式。涉及远程 PR 时确认目标分支、改动范围、需求覆盖、检查结果和未验证项；有必需 CI 检查时，核验最新 head 对应结果。合并策略沿用项目约定；解决冲突必须理解双方语义，不整文件选 ours/theirs。集成后重新验证关键行为并回读目标状态。
- **保护历史**：不擅自 force push、reset --hard、clean、删除分支/worktree、改写共享历史或变更全局 Git 配置；这些操作须明确授权并核对恢复材料。不擅自 rebase/cherry-pick 外来提交或处理用户的未提交改动。push/PR/合并/tag 等远程变更成功后回读确切目标，命令退出码不能代替结果核验。
- **明确验收入口与收尾**：每次交付必须明确告诉用户“看哪里”：可访问地址/启动命令、对应目录、分支、实际 commit、包含和未包含的功能、验证结果、未提交项、BD 状态和下一步。默认给一个明确验收目标；确需多个入口时逐一标注范围，不让用户猜哪个是最新。运行服务须核对实际运行代码版本，不能只报终端当前分支。未集成就明确没有完整汇总版本；任务完成、代码集成、已出版本、已部署并核验四种状态分别报告，不得以前一状态冒充后一。

## 硬边界与如实报告

- 提交只含本轮相关文件；本地数据/缓存/临时产物不提交
- 未提交改动先问归属，不擅自提交、不擅自丢弃
- **不擅自合并主干、打 tag、部署** —— 按上节分别核对授权；合并与生产发布分开，不能以开发或测试通过替代授权
- 不擅自改生产配置与权限；需要时先给「影响 + 回滚」
- 失败就说失败并贴证据；跳过哪步要写出来；**不许把"接口报错"说成"已通过"**
- 涉及数据/权限/外部系统的操作，先给影响与回滚再动手

## 发布验收清单

按阶段检查；不适用项写明理由，不能冒充通过。生产检查只适用于存在生产部署的项目。

### 发布前门禁

- [ ] 全量验证在隔离环境通过（记录结果与耗时）
- [ ] 静态/迁移/安全检查通过
- [ ] 冒烟闸按形态走过一遍
- [ ] `git status` 核对：只动了预期文件
- [ ] 产物从 tag 干净构建，不含密钥或本地数据
- [ ] 生产已备份（数据 + 配置 + 旧版本标识），路径已记录
- [ ] 人已确认需要主观判断的效果；纯客观任务按约定断言验收
- [ ] 回滚触发条件、步骤、兼容性和授权范围明确；L2 已在隔离环境验证

### 版本交付核对

- [ ] 版本对应确切 tag/commit 与集成基线，变更清单关联 PR/BD，未包含项明确
- [ ] 构建产物已实际验证；身份、位置和证据已记录；Release/内部记录与实际产物相符
- [ ] 已出版本与已部署分开报告；无部署需求时不执行生产步骤

### 部署后验证

- [ ] 运行端实际产物与验证产物身份对应，挂载/旧进程未造成版本错配
- [ ] 部署后健康检查正常、日志无异常
- [ ] 关键行为在生产抽查过（只读方式）
### 交付完成

- [ ] 回滚方式与材料写进交付报告
- [ ] 未完成/存疑项明确列出
